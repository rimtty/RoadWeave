# Webデザイン13〜16のLVGL移植：実験結果と課題

実験日：2026-09-06。RoadWeaveのWebデザインカタログ13〜16を対象に、WindowsとESP32-S3で共用するLVGLコードへの移植を検証した。

4つの主画面について、図形・文字・状態変化・左右スワイプをネイティブ描画で再現し、Windowsの実SDLウィンドウで確認できた。画像・入力を含むCTestは28/28成功し、ESP32-S3向けビルドも成功した。一方で、実機上の性能・視認性・物理タッチは未検証であり、製品としてのUI/UX評価は引き続き必要である。

この実験で得た知見は、**デザインへの忠実度、状態表示の意味、動的な描画の安定性、入力の正しさ、実機の制約をそれぞれ検証する必要がある**という点にある。本書はその判断と根拠を残す。

参照元：`design/web-poc/app/explore/collection.tsx` の13〜16、`explore.css`、`demo/graphics.tsx`。状態の理解には `demo/model.ts` も用いる。移植時には既存のGROUP/RADAR/CONVOYを維持した。

再利用する手順は[プロジェクトスキル](../../../../.agents/skills/roadweave-lvgl-porting/SKILL.md)に整理している。

## 再現方針

- Webの300px幅のカードを基準に、240pxへ80%縮小。高さ400px相当の320pxに収める。黒緑の背景、細い輪郭、余白、赤いアクセント、5×7ドットの字形、波形47×13、レーダーの3本のドット円、計器の2×2配置を引き継ぐ。
- ドット・波形・円・計器はLVGLの描画API、文字は同梱するライセンス付きサブセットフォントで描画。スクリーンショットを貼る実装にはしない。WebとLVGLのアンチエイリアスおよびRGB565量子化による差は許容し、配置・内容・字形を比較する。
- 初期状態はWebと同じAKI前方120m、REN後方85m、MEI後方240m、4人、受信中。状態更新で数字、発話、リンク、古い位置情報を描き分ける。
- 描画コードは実機とPCで共用。Windowsの追加シナリオで13〜16を直接起動・PNG保存できるようにする。

## タッチ操作

- 指を左へ動かす：13→14→15→16→13。右へ動かす：逆順。すべて同じ階層の画面なので、右スワイプが前の画面へ戻る操作になる。
- 4画面は循環する。端で操作不能にせず、画面上部のRW番号で現在位置を確認できる。新しい戻る／次へボタンは足さず、元のデザインを保つ。
- 横移動40論理px以上、横移動が縦の1.5倍以上、1秒以内の操作を解放時に1回だけ受理。短いタップ、縦方向、斜め、長押し、画面外へのキャンセルは切替しない。
- 縦方向は未割当。画面上のタップ／スワイプで送信は開始しない。PTTは物理入力を想定し、PCでは状態シナリオで表示を確認する。

## 採用した検証手順

1. Webの4画面を実ブラウザで描画し、座標・色・文字とPNGを参照する。
2. LVGLの4画面を240×320で保存し、Webと並べて確認する。初期画像を承認後に回帰用基準に登録する。
3. 左右の巡回、1操作1遷移、縦・斜め・短距離・キャンセルの抑止、状態保持を入力テストで確認する。
4. 受信・送信・待受・ミュート・通信断・古い位置・数値変更を検証。従来16テストも維持する。
5. Windowsの実SDLウィンドウで4画面とマウスドラッグによるスワイプを確認し、起動した状態で引き渡す。
6. ESP32-S3向けビルドで共通コード／フォントの互換性を確認。実機の描画速度と物理タッチは別途測定する。

## 起動・操作

リポジトリルートで実行する。

```powershell
.\firmware\scripts\ui-sim.ps1 -Scenario dot13 -Zoom 2
# 静止状態を見比べる場合
.\firmware\scripts\ui-sim.ps1 -Scenario dot14 -Zoom 1 -Paused
# 既存テストも含めて実行
.\firmware\scripts\ui-sim.ps1 -Action Test
```

左右ドラッグが液晶のスワイプに相当する。4/5/6/7キーで13/14/15/16を直接選択できる。Zは倍率、Spaceは模擬時刻と波形の停止／再開、Sは240×320 PNG保存。G=待受、X=受信、T=送信、B=空き待ち、D=位置未更新、L=切断、M=受信ミュート。状態キーは現在のDot画面を維持する。4〜7キーは初期の受信状態へ戻す。

ESP32ではmenuconfigの`RW_UI_DOT_STUDY`を13〜16に設定し、`RW_UI_SIMULATE=y`で同じサンプルを表示できる。デフォルト0では従来画面が起動する。今回はUSB書き込みは行っていない。

## 検証結果（2026-09-06）

- ChromeでWebの4案を描画し、DOM座標・色・文字・SVG字形を確認。`reference/web-dot13.png`〜`web-dot16.png`が240×320に正規化した比較元、`reference/source.json`が参照したWebソースのSHA256。
- `build/results/dot-comparison.png`でWebとLVGLを横に並べ、数字・日本語・配置・配色を目視確認。字形と情報階層を再現。RGB565、整数座標の丸め、フォントのラスタライズで微小な差がある。丸角外側はWebカードの背景色ではなく液晶用の背景色を使う。
- MSVCビルド成功。従来16件を維持し、画像11件とDot操作1件を追加した **CTest 28/28成功**。
- SDL dummyドライバーでも1/2/3倍ごとに左右4画面を巡回、縦方向の誤操作抑止、倍率変更前後の描画一致を確認。Headless入力テストでは短距離・斜め・長押し・キャンセル・操作中の画面変更・状態保持も確認。
- 状態テストでは、古い／切断中の距離を変更しても画像が変わらないことを確認し、古い位置の漏れを防止。待受／ミュート中の波形は停止し、送信の波形は受信ミュートから独立する。長い数値はドットの字形を保って縮小表示する。
- Windowsの実SDLウィンドウでも13→14→15→16と右スワイプで戻る操作を確認。自動テストが使う同じ共通描画・入力コードで動作している。
- 部分更新の固定領域を保持するため、カスタム画面の不透明背景をLVGLへ明示。Windows操作ツールの画像で一部の表示欠けが見られたため、見た目の確認だけに依存せずHeadless／SDLの両テストに波形以外の画素一致を追加。さらに実Windows SDLレンダラーの画素を読み戻し、26段階の波形更新とミュート／TX／切断でLVGLのRGB565画像と一致することを確認した。キャプチャ上の欠けの原因をすべて特定したわけではない。
- ESP-IDF 5.4.4 / ESP32-S3、`RW_UI_DOT_STUDY=13`でビルド成功。バイナリ`0xae6f0`バイト、1MiBのアプリ領域に32%の余裕。実機のFPS／RAMピーク／液晶の見やすさ／物理タッチは未測定。

比較画像を再作成する場合はWeb開発サーバーを起動し、候補画像生成後に`node firmware/experiments/ui_lvgl/pc/capture-web-reference.mjs`を実行する。Webのインストール済みPlaywrightとChromeを使う。この処理は比較用アーティファクトのみ更新し、Webのソースは変更しない。通常のビルド／CTestはWeb・Chrome・フォント生成ツールに依存しない。

この移植の対象は13〜16の主画面。Webデモの車列／GPS詳細、複数話者専用レイアウト、PTT許可制御、実音声処理は含まない。色・図形は動的に描画し、状態表示は既存の単一音声状態モデルを使う。日本語の補助文字は忠実な縮小に合わせて7〜10pxなので、製品向けの視認性評価では文字を大きくする案も比較する。

## 実験で明らかになった課題

### 1. 縮小による忠実な再現と、液晶での読みやすさ

Webカードを80%に縮小することで配置と情報階層は引き継げたが、RGB565の色量子化、整数座標への丸め、アンチエイリアスの違いにより、細い線や文字の縁まで完全には一致しない。また、日本語の補助文字が7〜10pxとなり、見た目を再現できたことだけでは読みやすさを保証できない。

今回の比較では、配置・内容・字形の一致と、描画方式による微小な差を分けて判断した。Windowsの等倍表示は論理ピクセルの確認に使えるが、OSのDPI拡大が加わるため、実液晶と同じ物理サイズでの評価にはならない。次は実際の液晶で確認し、必要なら補助文字の拡大と余白の再配分をデザイン変更として比較する。

### 2. フォントのウェイトと日本語サブセットの管理

同じフォント名でも、可変フォントの既定ウェイトがWebで指定した400と一致せず、変換しただけでは文字が細くなる問題があった。Geist MonoとNoto Sans JPをウェイト400に固定してからLVGL用へ変換した。

日本語は必要な字形だけを含めるため、文字の追加を生成対象に反映しないと欠けが生じる。今回の生成処理は `ui_dot.c` の非ASCII文字を収集する方式とし、生成Cとライセンスを残した。今後、表示文言を別ファイルや外部データへ広げる場合には、抽出元と対応文字の範囲も見直す必要がある。通常ビルドでフォントの取得・変換を行わない構成は維持する。

### 3. 部分更新と実際の表示結果の切り分け

波形だけを更新する場合でも、固定部分の保持、背景の不透明度、無効化範囲が正しく定義されている必要がある。SDLの倍率変更では表示バッファが再確保されるため、論理解像度が変わらなくても全面を再描画する対応が必要だった。

カスタム画面の背景指定と倍率変更時の全面無効化に加え、更新領域以外の画素が変化しないテストを追加した。さらに `SDL_RenderReadPixels` で実Windows SDLレンダラーから画素を読み戻し、複数の波形位相と状態変化でLVGLのRGB565バッファとの一致を確認した。

ただし、操作ツールの画像に見えた欠けについて、アプリの描画とキャプチャ経路のどちらが原因だったかをすべて確定できたわけではない。「PNGが正常だから実表示も正常」「背景指定を直したからすべて解消」とは判断せず、論理バッファ・SDL表示面・キャプチャ画像を別々に検証する必要がある。

### 4. 静止デザインに含まれない操作仕様

カタログの見た目だけでは、スワイプ方向、画面の循環、キャンセル、遷移後の状態保持は決まらない。今回は同階層の4画面と解釈し、左で次・右で前へ循環する操作を設計した。短距離・縦・斜め・長押し・キャンセルを除外し、1回の操作で1回だけ遷移することを検証した。

Windows側では、通常のキーイベントに加えて文字入力イベントだけが届く操作経路があり、両方への対応と二重実行の抑止も必要だった。これはPC検証環境の課題であり、ESP32のタッチ入力とは分けて扱う。

実タッチパネルでのノイズや操作感はまだ評価していない。今回の40px・1秒という条件は実験の設定値であり、他の画面や実機へそのまま適用できると結論づけない。

### 5. 初期表示以外の状態での情報の正しさ

初期画像が似ていても、通信断、古い位置、ミュート、長い数値などで情報が誤って伝わる可能性がある。今回は、古い／切断中の距離を変更しても画像が変わらないこと、待受／ミュート中は波形を停止すること、送信波形は受信ミュートから独立すること、5桁の距離でも表示が収まることを検証した。

画面遷移時には、画面だけでなく音声・リンクなどの状態を保持する必要がある。今後、複数話者や実際の通信モデルへ接続する段階では、単一音声状態の模擬モデルでは表せない状態と遷移を追加し、対応する表示・操作テストを増やす必要がある。

### 6. PCでの成功とESP32での実用性能

共通の描画コードとフォントでESP32-S3向けビルドが通り、今回の構成は1MiBのアプリ領域に収まった。ただし、32%の余裕はアプリ格納領域の値であり、RAMの余裕や実行性能を示すものではない。

実機のFPS、フレーム時間、RAMピーク、SPI転送時間、音声処理との同時動作は未測定である。Windowsで滑らかに動いたことからESP32でも十分な性能があるとは断定できない。機能を追加する前後で、同じシナリオを使って実機の負荷を測る必要がある。

## 検証方法から得られた教訓

| 確認方法 | 確認できること | それだけでは確認できないこと |
|---|---|---|
| WebとLVGLの画像を並べて確認 | デザインとの対応、配置、字形、情報の欠落 | 操作の正しさ、長時間の描画安定性 |
| 固定データ・固定時刻の画像回帰テスト | 採用した描画からの意図しない変化 | 基準画像そのものの正しさ、デザインへの忠実度 |
| 入力・状態テスト | 遷移、無効操作、キャンセル、状態保持 | 実タッチパネルの感触やノイズ |
| 実SDLの操作と画素読み戻し | PCの入力経路、表示面、更新時の整合性 | 実液晶の見やすさ、ESP32の速度 |
| ESP32-S3向けビルド | 共通コードの互換性、アプリ領域への収容 | 実行時RAM、FPS、通信・音声との競合 |

基準画像は、実際のデザインと比較して意図した結果と判断した後に登録する。LVGL同士の回帰比較は許容差0を維持し、差分が出た理由を確認する。失敗を消すための基準更新は行わない。新しい検証を追加する際は、既存の成功件数ではなく、その変更で壊れ得る振る舞いに対応させる。

## 次に行う検証

以下は今回の結果を踏まえた次段階の候補であり、実施済みの結果ではない。

| 優先 | 検証対象 | 確認内容と判断材料 |
|---|---|---|
| 1 | 実液晶での視認性 | 補助文字、細線、赤いアクセントを想定距離・明るさで確認。文字拡大案と現行案を比較する |
| 2 | 描画と音声の同時動作 | 各画面と波形更新でフレーム時間・転送時間・RAMピークを測り、音声処理への影響を確認する |
| 3 | 物理タッチ | 左右スワイプの認識、誤切替、キャンセル、端の操作を確認し、しきい値を調整する |
| 4 | 実データへの接続 | 更新遅延・切断・復帰・複数話者などの状態を定義し、表示と操作を対応させる |
| 5 | デザインの拡張 | 詳細画面や新しいカタログ案へ同じ移植手順を適用し、共通化できる描画部品を判断する |

性能や操作性の合格値は、実機構成と製品要件に合わせて別途定める。今回の実験結果から未測定の数値目標を達成済みとは扱わない。
