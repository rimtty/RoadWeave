# P0-A 当日実証・実装計画（2026-09-19）

対象は[残課題整理](p0-a-open-items-2026-09-19.md)のうち、8時間連続運転を除く項目。
ユーザー指示により、計画・進行管理をAstra、実装をSolが担当する。
計画の作成は試験の成功を意味しない。結果は別の実証レポートへ実測値と証跡を記録する。

## 到達目標と固定条件

- 今日の成果を機能別ブランチ・レビュー・マージで保存し、実機に書いたコミットと設定を追跡できるようにする。
- 2台のHaLow接続を中心に、IP取得、有限の継続通信、障害後の自動復帰、1/2 MHz比較を実機で検証する。
- 起動・電源・受入の残項目も実際に着手する。設備や手作業が必要な項目は、未実施理由と必要物を残す。
- 8時間soakは実行も予約もしない。数分の計測を長期安定性の証明にしない。
- 無線経路はESP32-S3 → SPI → Wio-WM6180/MM6108 → HaLowのみ。ESP32内蔵Wi-Fiを初期化しない。
- アンテナ装着と使用条件確認済みという既存のユーザー申告を使用する。US規制DB・1 dBm上限設定を継続し、実出力とは区別する。
- ESP-IDF v5.4.4 / morsemicro/halow 2.11.2-esp32-2を維持。BUSY/WAKE未配線、PS無効、既存board adapterを前提とする。

## 実施前ゲート

1. 既存成果のPRをマージし、mainがクリーンであることを記録する。
2. COM番号だけに依存せず、USBとESP32 MACを照合する。既知個体はCOM4相当 `44:B1:76:B0:57:20`、COM5相当 `44:B1:76:B0:57:1C`、COM6相当 `44:B1:76:AE:C4:90`。
3. 現状のフラッシュ保存・復元手順、SDK、ビルド環境、アンテナ条件、電源制御／電流測定設備の有無を確認する。
4. COMポート操作・書込み・リセットは主担当だけが実行する。Sol担当は同時に実機を操作しない。
5. 既存FWはAP最大STA数1、両STAが `192.168.50.2`。これを解消するまでSTA2台を同時に走らせない。

## Solへの実装仕様

### 有限継続・復帰・統計

- 既存20往復モードとRF無効preflightを保持し、設定可能な有限試験時間、送信間隔、payload長を追加する。
- 比較用の初期条件はpayload 256 bytes、送信間隔250 ms、計測120秒以上。必要な変更は各比較runに同じ条件で適用する。
- 固有node IDと固定IP、AP最大STA数2を設定可能にし、同時通信を将来検証できる状態にする。設定追加だけで3台試験完了とはしない。
- AP/STA双方に終了期限を設け、全ての正常／異常終了でsocketを閉じ、無線停止と最終結果をログに残す。
- associationとIP readinessを別々に判定する。切断でIP-readyをクリアし、IP変化後は古いbindを使い続けない。
- STAの接続要求を無限ループで連打しない。SDKの再試行状態を尊重し、必要な再接続操作はイベントcallback外の制御taskで行う。
- AP停止・復帰、STA再起動、STAの明示的切断・再接続を識別できる注入方法を用意する。注入時刻と状態遷移を出力する。
- nonce、sequence、payload一致でechoを検証する。重複／遅延／別runの返信で受信成功数を水増ししない。
- 時刻、試行／送信成功／受信成功／timeout／duplicate／invalid、payload bytes、RTT、再接続回数、heap/min heap、reset reasonを記録する。
- 実測RSSI、SDKが取得可能なUMAC/RC統計の前後値・差分を記録する。取得失敗は `unavailable` とし0に変換しない。
- `mmwlan_get_rc_stats()` は必ず対応するfreeを呼ぶ。RC送信回数と成功回数の差を、定義確認なしに「無線再送回数」と呼ばない。
- SNRはRSSIだけでは求められない。noise/SNRの有効なSDK計測がなければ未取得として残す。
- stop-and-wait echoのbytes/timeは、その負荷条件でのアプリケーションgoodput。最大スループットとは記載しない。
- 1 MHz/2 MHzでログレベル・payload・間隔・個体・配置・電力設定を揃える。初回ARP／ウォームアップは全体と分けて集計する。

### DHCP

既存wrapperはAPでも `ESP_NETIF_DEFAULT_WIFI_STA()` でnetifを作るため、単にDHCPサーバ開始を追加するだけでは不十分。
固定SDKの実装を確認し、AP用netifのDHCPサーバ対応・HaLow RX/TX接続・MAC・生命周期を明示したadapterを設計する。
managed componentをローカル編集しただけの修正は禁止し、再ビルド可能なプロジェクト内実装にする。
STA側はDHCPを使用したこと、取得したIP/gateway/netmask、取得時刻を記録する。
固定IPへの暗黙fallbackでDHCP成功と判定しない。

### 実行・集計ツール

- COM/MAC、Git commit、dirty有無、binary SHA256、公開可能な設定、開始終了時刻、操作履歴、raw log pathをmanifestへ保存する。
- PSKは公開設定／コマンド出力／ログ／レポートから除外する。raw logにも秘密が含まれうるため公開前に確認する。
- host時刻とdevice uptimeを区別し、機器再起動をまたぐ復帰時間にはhost側の単調時計を使う。
- timeout・欠損した最終行・device reset・プロセス中断をPASSにしない。最終集計と個別echo数を照合する。
- RTT中央値/p95/最大、定義付きloss率、goodput、heap傾向、障害から最初の正常echoまでの時間を出す。
- 物理電源断とserial resetを操作種別で区別する。自動でcold boot数を偽装しない。

## 当日試験表

以下の数値は今回のベンチ用の暫定判定基準。製品・音声の受入基準とは別。
障害を意図している区間の損失は、平常区間のlossと分ける。

| ID | 操作／件数 | PASS条件・記録 |
|---|---|---|
| T01 基本回帰 | AP＋STA1、AP＋STA2を順番に各20往復 | 各20/20 payload一致、panicなし、終了時無線停止 |
| T02 平常継続 | 2台で各条件120秒以上、warmup後200送信以上 | 平常区間の送信成功に対する受信率99%以上、panic/resetなし。RTT/heapを記録。閾値未達はFAILとして原因調査 |
| T03 AP再起動 | 同じSTAを稼働したままAPリセット、3回 | 各回AP_READYから60秒以内にSTA手操作なしで正常echo再開、連続20往復成功。障害開始からの全停止時間も記録 |
| T04 STA再起動 | APを稼働したままSTAリセット、3回 | 各回起動から60秒以内にIP取得と正常echo、連続20往復成功。AP無操作 |
| T05 一時通信断 | AP無線機能停止10秒→再開、3回 | 各回再開後60秒以内に自動echo復帰。AP再起動とは別記録。これは電波伝搬によるlink lossの代用証明ではない |
| T06 DHCP | 両STAを順番にクライアントとして取得、T03/T04の組合せ | 両個体のDHCP由来アドレスとUDP成功、AP/STA再起動後のIP状態が正常。設定がDHCPというだけではPASSにしない |
| T07 1/2 MHz比較 | 規制DBで有効な各幅、同じ2台・負荷で各3回 | 各回T02を満たす。周波数・帯域・RSSI・loss・RTT・goodput・SDK統計・取得できない項目を記録。2 MHzの方が速いことを必須にしない |
| T08 起動再現性 | 2組それぞれ実電源OFF→ONを50回 | 各50/50でSPI/MM6108初期化成功。電源断の操作・保持時間・再列挙・boot logを保存。serial resetを含めない |
| T09 短時間再初期化 | T08用電源制御が無い場合にも通常reset/無線再起動を反復 | 件数・警告頻度・成功率を報告する補助試験。cold boot50回の条件は未達のまま |
| T10 ボード警告 | 各起動と障害復帰logを照合 | `Address base set failed` / unknown TLV等を分類、後続FW起動・通信成功との対応を記録。無根拠なログ抑制や「無害」断定をしない |
| T11 電源 | 計測器を使いidle/RX/TX、rail電圧を実測 | 測定点、USB全体かモジュール単体か、機器型番、sampling/帯域、平均/peakと通信条件を記録。低速USBメーター値をRF burst peakと呼ばない |
| T12 受入 | 3個体の物理ラベル・基板組合せ・アンテナ・外観・無通電導通・LED | 写真／目視／計測の実証を個体へ対応付ける。USB認識から外観・導通・LED目視を推定しない |

T03/T04のserial resetは復帰試験として有効だが、T08とは異なる。
T05はAPサービス断であり、遮蔽・距離等によるRF link lossとは区別する。
必要な設備がない場合でも、実施可能なT01〜T07/T09/T10を止めずに進める。
T11のidleは「接続済み・アプリ送信なし・PS無効」と定義し、deep sleep電流とは区別する。
echo試験中の値はTX/RX混合である。個別RX/TX負荷が作れない場合は混合状態として報告する。

## 手元の設備・ユーザー作業に依存する項目

- **cold boot**: 真のUSB VBUS断を行う外部switch/relay/対応hub、または人の抜き差しが必要。
  OS上のdevice disable、USB再列挙、DTR/RTS操作だけでは電源断の証拠にならない。
- **電流／rail電圧**: USBから一般に実電流値を取得できるとは限らない。接続された測定器やテレメトリの存在を先に調べる。
- **外観／導通／ラベル／LED**: 現物操作と目視、無通電計測の結果が必要。ソフトウェアだけで完了させない。
- **XIAO単体smoke**: HaLowを装着した成功ログは全台の単体検査記録の代わりにならない。脱着検査の可否を別記録する。

これらが未実施なら、本日のソフト実証が成功してもP0-A全体を完了にしない。
BUSY未配線は「観測FAILのまま基板非適用と理由を記す」扱いとし、公式Porting Assistant全項目PASSとは表現しない。

## 追加試験：3台同時

2台試験が安定し時間が残る場合、AP最大STA数2、DHCPまたは固有固定IP、個体ID、peer別検証／統計を実装する。
2STAが同時に各200送信以上、各受信率99%以上を満たすことと、一方のSTA再起動中に他方が動き続けることを確認する。
元のP0-A必須条件ではないため、未実施を基本2台通信のFAILにはしない。

## 進行管理とレポート

1. Astraが既存成果保存・設備棚卸しを完了し、Sol2担当へFW／host toolsを割り当てる。
2. ログ仕様を合わせて実装・レビュー・ビルドし、主担当だけがT01/T02を実機実行する。
3. 復帰機能のPRを実機結果付きでマージ。DHCP実装へ進み、T03〜T07を実行する。
4. 電源・計測設備がある項目を実測し、無い項目は明確な未実施理由と必要物を記録する。
5. 最終レポートに「PASS／FAIL／未実施／非適用」を分けて記載し、実機に残るFWと再起動時の挙動を明記する。
6. 結果・手順・残課題のPRを作成してマージする。8時間soakは残件として維持する。

最低限の成果物は、機能PR、commit/binary対応表、試験manifest、公開可能なraw log、比較表、復帰時間表、設備依存残件、最終設置FWの一覧。
試験がFAILした場合も、再現条件と修正前後の証跡を残す。成功ログだけを選んで「全部完了」としない。
