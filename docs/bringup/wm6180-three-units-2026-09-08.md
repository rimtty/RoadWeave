# Wio-WM6180 3組のSPI診断結果（2026-09-08）

追加2組のMM6108 SPI診断はPASS。前回の1組と合わせ、異なるESP32 MACの3組すべてでSPI起動、chip ID、bulk転送、raw throughputがPASSした。
BUSY検査は全組でFAILし、Wio-WM6180の既知のBUSY未配線仕様と整合する。完全版Porting Assistantの全項目合格ではない。
無線FWのロード・起動、RF送信、AP/STA接続は行っていない。

## 個体と結果

ポート番号は検査時のWindows上の値。恒久的な識別にはESP32 MACを使う。物理ラベルRW-N01〜03の貼付・対応確認は未実施。

| ESP32 MAC | USB | 検査 | Flash / PSRAM | MM6108 ID | ID反復 | SPI bulk | raw SPI転送 |
|---|---|---|---|---|---|---|---|
| 44:b1:76:b0:57:1c | COM5 | 前回実施 | 8 / 8 MiB、PSRAM test OK | 0x0306 | 100/100一致 | PASS | 7,522 kbit/s |
| 44:b1:76:b0:57:20 | COM4 | 今回実施 | 8 / 8 MiB、PSRAM test OK | 0x0306 | 100/100一致 | PASS | 7,522 kbit/s |
| 44:b1:76:ae:c4:90 | COM6 | 今回実施 | 8 / 8 MiB、PSRAM test OK | 0x0306 | 100/100一致 | PASS | 7,522 kbit/s |

追加2台ともESP32-S3 QFN56 rev.0.2、GD Flash（manufacturer c8 / device 4017）、AP Octal PSRAM、CPU 240 MHz。
MM6108 IDは機種識別値であり、モジュール固有のシリアル番号ではない。
今回の結果は接続されたESP32とWM6180の組に対応する。WM6180自体の個体ラベルは別途必要。

## 条件と確認範囲

- ESP-IDF v5.4.4、Morse component `2.11.2-esp32-2`。
- 前回と同一のSPI専用診断バイナリを使用。SPI2 / mode 0 / 設定40 MHz / DMA。
- 診断アプリSHA256: `094ca359f0e6de9e643187f6c641ba46e7818a67d9c159b862889be9d1531828`。
- 実行時repoはmain `b04144f7efbecd69a47eacad1b59988b9f4b970f`。再利用した診断バイナリのapp versionは`3725b38-dirty`であり、今回mainから再ビルドしたものではない。
- chip ID反復はトランスポートCRCを検査。bulkは1,496 bytesの書込み・読出し一致を検査。
- 追加2台ともraw throughputは2,501 ms、786往復、読み書き合計2,351,712 bytes。無線スループットではない。
- 各ログの総計は7段階中4 PASS、1 FAIL（BUSY）、2 no result（初期化・リセット）、0 skipped。
- 追加2台ともBUSY出力レジスタは0→1に変化したが、ESP32 GPIO5はLOWのまま。
- GPIO snapshotは両個体でBUSY=0、IRQ=1、MISO=1、出力ラッチ`0x12`。端子電圧の実測やIRQ機能試験ではない。
- RESET_N=GPIO1、WAKE=2、IRQ=3、CS=4、BUSY=5、SCK=7、MISO=8、MOSI=9。

検査方法、BUSY/WAKE未配線の根拠、GPIO設定の詳細は[前回の診断記録](wm6180-spi-2026-09-08.md)を参照。

## USB接続とバックアップ

COM6は当初ASMedia USB4側コントローラー配下で認識。全Flash読出しが2回、転送中断で失敗した。切断・ケーブル・ホスト側などの原因は特定していない。
その後、ユーザーがUSB接続を変更し、追加2台がそれぞれAMD USBコントローラー配下で認識された。

通常USB接続後は512 KiB × 16区間の読出しが両個体とも全区間初回成功。各区間でesptoolの出力MACを照合してから結合し、
全8,388,608 bytesを`esptool verify_flash`で実機と比較してdigest一致を確認した後に診断FWを書き込んだ。
接続経路と読出し方法の両方を変更したため、成功をもってThunderbolt自体の不具合とは断定しない。

## 終了状態と残件

追加2台ともSPI診断FWを残した。診断終了時に`mmhal_wlan_deinit()`を実行し、WM6180をRESET_N LOWで保持する。
ESP32をリセットすると同じSPI診断を再実行する。元のアプリには戻していない。

この結果で3組のSPI通信とメモリ起動検査は確認できたが、外観・ヘッダー・電源電圧の実測、全台のXIAO単体試験、FW/BCF起動、IRQ動作、cold boot 50回、AP/STA・長時間試験は完了扱いにしない。
RF試験部材と音声部材はユーザー申告で未到着。今回の追加検査で無線送受信の工程へは進んでいない。
