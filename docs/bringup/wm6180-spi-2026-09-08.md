# XIAO ESP32S3 + Wio-WM6180 SPI診断（2026-09-08）

SPIの起動・MM6108識別・データ読み書きはPASS。BUSY信号はESP32側で変化せず、Wio-WM6180の既知の未配線仕様と整合した。
無線FWをMM6108へロード・起動せず、RF送信やAP/STA接続は行っていない。

## 実機と実行環境

| 項目 | 確認値 |

| 基板 | ユーザー申告: Seeed Wio-WM6180 + XIAO ESP32S3 |
| Windows USB | COM5、VID 303A / PID 1001、正常認識 |
| ESP32 | ESP32-S3 QFN56 rev.0.2、MAC 44:b1:76:b0:57:1c |
| Flash | GD 8 MiB、QIO 80 MHz |
| PSRAM | AP 8 MiB Octal 80 MHz、`SPI SRAM memory test OK` |
| CPU | 240 MHz |
| ESP-IDF | v5.4.4 |
| Morse component | morsemicro/halow 2.11.2-esp32-2（完全一致で固定） |
| Repo | main `3725b38`、事前に`git pull --ff-only`実施、origin/mainと一致 |
| SPI | 公式shimのSPI2、mode 0、設定40 MHz、DMA使用。波形・実クロック周波数の実測は未実施 |

接続時のFlashには`Hello from Seeed Studio XIAO ESP32-S3 Sense`とカメラ未検出エラーを出すアプリが入っていた。
診断前にFlash全8,388,608 bytesをバックアップし、`esptool verify_flash`で実機とのdigest一致を確認した。

バックアップSHA256: `25d7c100219d86dc0d1808913501b6cd6783a594ac0bb3dcf93c45e63be75511`

## 試験方法

公式`porting_assistant`を生成し、`firmware/porting_assistant/`（Git管理外）で以下の診断用変更を行った。

- OS・FW/BCFファイル検査を実行対象から外し、SPI初期化、ハードリセット、起動、chip ID、bulk転送、raw throughput、BUSYを実行。
- chip IDを追加で100回読み、値一致とトランスポートのCRC検査を確認。
- GPIO設定を`gpio_dump_io_configuration()`で出力。
- BUSY検査用に`CONFIG_HALOW_PS_MODE=y`を明示。これを無効にするとBUSY HALが固定falseになるため、実配線検査には使えない。
- 初回はBUSY失敗で後続転送試験がスキップされた。2回目はBUSYを最後に移し、転送試験とBUSYの結果を分けた。
- MM6108側GPIO出力許可・出力値レジスタを読み返し、書き込み成功とESP32入力の不一致を確認。
- 終了時に`mmhal_wlan_deinit()`を呼び、RESET_NをLOW、SPI busを解放。

`mmwlan_boot`、`mmhalow_init`、無線接続・送信処理は呼ばない。countryは設定上JPだが、このSPI診断では無線設定に使用していない。
診断結果は完全版Porting Assistant全項目の合格や、RF試験への移行承認を意味しない。

## 最終試験結果

| 試験 | 結果 |
|---|---|
| SPI起動 | PASS |
| MM6108 chip ID | `0x00000306`、追加100/100回一致 |
| bulk write/read | 1,496 bytesのパターン一致、PASS |
| raw throughput | 2,501 ms、786往復、合計2,351,712 bytes、7,522 kbit/s、PASS |
| BUSY | MM6108側OE=1、OUT=0→1をSPIで読み返せたが、ESP32 GPIO5は0のまま |
| 総計 | 7段階中4 PASS、BUSY 1 FAIL、初期化/リセット2段階は公式実装上no result |

7.522 Mbit/sはSPIの読み書き合計の転送速度であり、無線スループットではない。
BUSYの最終状態は以下のとおり（すべてレジスタアクセスret=0）。

```text
MM6108 BUSY LOW:  OE=0x00000001 OUT=0x00000000 host=0
MM6108 BUSY HIGH: OE=0x00000001 OUT=0x00000001 host=0
ROADWEAVE_SPI_RESULT=PASS
ROADWEAVE_BUSY_RESULT=FAIL_OR_SKIPPED
ROADWEAVE_SPI_DONE
```

## GPIO設定と観測

以下は診断中の設定。出力のHIGH/LOWは出力ラッチからの値であり、端子電圧の実測ではない。

| 信号 | ESP32 GPIO | 診断中の設定・観測 |
|---|---:|---|
| RESET_N | 1 | 出力、診断後半のラッチHIGH、終了時LOWに設定 |
| WAKE | 2 | 出力、ラッチLOW。回路図R10 DNPでモジュールへの導通は期待しない |
| SPI IRQ | 3 | 入力、pullなし、最終サンプルHIGH。割り込み発生の試験は未実施 |
| SPI CS | 4 | ソフトウェア制御出力、最終ラッチHIGH |
| BUSY | 5 | 入力、pulldownあり、モジュール出力変更にかかわらずLOW |
| SPI SCK | 7 | SPI2 matrix、SigOut/In ID 101 |
| SPI MISO | 8 | SPI2 matrix、SigOut/In ID 102、最終入力HIGH |
| SPI MOSI | 9 | SPI2 matrix、SigOut/In ID 103 |

GPIO19/20はUSBに使用。未使用GPIOの外部配線や電源電圧・電流は今回測定していない。

## BUSY失敗の解釈

[Seeed公式回路図（2024-11-07、V30）](https://files.seeedstudio.com/wiki/wifi_halow/res/WI-FI_HALOW_FGH100M_EXT01_V30_SCH_20241107.pdf)を図として確認した。
R17はモジュールGPIO0/BUSYとXIAO D4の間、R10はWAKEUP_INとD1の間にあり、両方DNP。
WAKEUP_INにはモジュール側3.3 Vへの10 kΩ pull-up、BUSYにはモジュール側10 kΩ pull-downがある。

[Morse Microの回答（2025-11-03）](https://community.morsemicro.com/t/mm-iot-esp32-porting-assistant-error-seeed-xiao-halow/1011/2)も
Seeed XIAO HaLowのBUSY未配線を明記し、Porting AssistantのBUSY検査除外と、チップ起動後の省電力無効化を案内している。
今回の実測はこの仕様と整合する。実機の抵抗実装を目視・導通測定したわけではないため、個体のR17実装状態そのものを断定はしない。

今後の通信アプリでは標準基板に対して省電力を無効化し、BUSY依存のsleep/wake動作を使わない。
BUSY配線を追加する改造は今回実施していない。
